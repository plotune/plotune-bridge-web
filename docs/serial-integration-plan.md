# Bridge Serial integration plan for Bridge Web

**Status:** integration plan and future acceptance target. The accompanying local WebSocket preview and mock browser tests implement only a subset of Phase 2; the scenarios below are a roadmap, not a claim that every scenario or hardware behavior is verified. Bridge Serial contract v0.1.0 is the draft baseline.

## Decisions

1. Add Serial as a distinct device family and protocol session, reusing the workspace shell, device hub, transport adapters, notices, persistence conventions, and bounded trace concepts. Do not force serial bytes into CAN frame types or CAN diagnostics.
2. Treat the descriptor as authoritative. The page renders only the modes and baud rates the device advertises, and labels each channel's current actual configuration. Unsupported devices and versions fail closed with an actionable compatibility notice.
3. Keep Serial's first UI as a byte-oriented terminal/trace with explicit hex and escaped-text views. Preserve original bytes, direction, channel, device timestamp, loss markers and UART error counters. Text is a view over bytes, never the stored representation.
4. Configuration is per channel and complete/atomic, matching `configure_channel`. Require RX stopped for that channel before applying it; do not silently reconfigure or restart a stream. Termination and bias controls appear only where meaningful, with the hardware default/off state visible.
5. A Serial device occupies one logical session regardless of channel count. A second connection replaces the first per contract; Bridge Web must explain replacement and must never retry or take over automatically.
6. Device-detected byte loss, unknown-count UART overruns, post-sequence event gaps, and browser trace eviction are separate visible categories. None is silently folded into another or represented as a precise byte position unless the contract supplies one.
7. Reuse existing local WebSocket and cloud WebRTC transports only after validating the framing and backpressure assumptions for sustained byte streams. The existing WebRTC path uses one reliable ordered data channel, which is semantically promising but does not establish supported serial throughput, latency, disconnect buffering, or browser compatibility.

## Current Web architecture to extend

Bridge Web already has a useful layered shape: `DeviceTransport` moves whole JSON contract messages, `DeviceSession` handles hello/request IDs/events/sequence gaps, each device store owns one session and trace, and the hub coordinates independent devices. `WebSocketTransport` enforces text JSON framing and bounded outbound buffering. `RemoteTransport` implements the same abstraction over a reliable ordered WebRTC data channel and retains cloud signaling for the connection lifetime. The mock Playwright server models the CAN contract, origin allow-list, replace-on-connect, close behavior and seeded streams; production-build Playwright tests use it over a real local WebSocket.

Serial should introduce `SerialDeviceSession` and Serial domain types/decoder rather than widen CAN `DeviceSession` until it becomes a protocol union. Add a capability discriminator to device identity/descriptor handling, then let the hub own a family-specific store behind a narrow common connection/notice interface. This keeps existing CAN panels and protocol decoders unchanged. Implement a `SerialTraceBuffer` (or shared generic bounded-row primitive) whose rows retain `Uint8Array` bytes and BigInt timestamps; render hex by default and offer escaped UTF-8 as a reversible convenience view. Never decode arbitrary serial data as JSON or assume valid UTF-8.

The first vertical slice should be local device connection, hello/version validation, descriptor/status, per-channel configure/start/stop, receive trace, transmit, statistics and loss presentation. Keep serial-specific settings and panels attached to the selected Serial device, just as current CAN settings and databases are device-specific. Device selection and workspace persistence may remember address/IDs and UI preferences, but must not replay configuration or start RX on reconnect.

## Capability-aware setup and live UX

- On connect, show a short staged connection status, then identify the device and both channels from `hello`. Validate contract version before exposing controls. The v0.1.0 schema requires exactly two channels, all three modes and the required standard rates; reject descriptors that do not meet that baseline.
- Per channel, show mode, baud, data bits, parity, stop bits, streaming status, queue depth/capacity, termination and bias. Present only `supported_modes` and `supported_baud_rates`; do not synthesize a missing capability. A null config is clearly “Not configured.”
- Provide a channel configuration form with mode, baud, character format, and applicable termination/bias toggles. Explain that changing a live channel requires stopping RX first. Apply one complete config; on `CHANNEL_BUSY` or validation failure retain the displayed effective settings and explain the response.
- Start RX only for explicitly selected, configured channels. A device may already be streaming after reconnect; report that truthfully and offer Stop/continue controls. Since the contract retains armed RX on link loss, reconnect must show the same stream state and original timestamps, and explain possible bounded-queue loss.
- Provide a bounded live byte trace with channel, device-relative time, RX/TX direction, bytes (hex), and inline loss/error markers. Chunk boundaries are transport buffering only: do not imply message or line boundaries. Provide copy/export as hex first; escaped text must preserve a way to recover the exact bytes. Bound TX payload by contract and UI policy, show “accepted/queued” separately from physical completion, and report later TX failure/counter changes.
- Show statistics per channel and distinguish received, forwarded, dropped, hardware overrun event/known overrun bytes, queue-overflow bytes, TX accepted/sent/failed, echo dropped, framing/parity errors and breaks. Reset follows contract semantics (settle queues and reset both channels); confirmation should describe the scope.
- At trace capacity, count evicted rows/bytes separately from device and transport loss. Keep the trace usable on narrow screens and keyboard/screen-reader accessible; do not put a high-rate byte stream into an unbounded DOM.

## Version negotiation and malformed peers

Send `hello` with the exact Serial contract version and client identity on each newly opened connection. Validate the complete descriptor and its capability values before storing it. Follow the Serial version rule: for 0.x, major and minor must match; patch differences are compatible. Reject unsupported major/minor, malformed uint64 timestamps, unknown enum values, impossible channel configs, invalid hex, or invalid event shapes as protocol errors; close rather than guessing. Keep request correlation and timeout behavior from CAN where compatible, with a Serial event sequence tracker that treats a gap as lost events (not known lost bytes). A reconnect always creates a new session and performs hello again; never replay configure/transmit/start requests automatically.

The contract has a potentially consequential open point: saved configuration persistence mechanism/timing is unspecified even though the contract requires reporting restored valid configuration. Before firmware claims SER-007 behavior, agree on persistence semantics and ensure hello accurately reports effective state. Web can display the returned state without deciding device persistence policy.

## Timestamps, ordering, and loss

Parse JSON integer tokens losslessly before JavaScript number conversion and preserve them as `BigInt` through trace, formatting and export; converting an already-rounded `number` is insufficient. `timestamp_ns` is device monotonic time of the first byte in a chunk, or loss-report time for an empty loss-only event; it is not browser receipt time. Preserve per-channel capture order. Do not compare monotonic values across different devices as a shared clock. A device clock sample may support a clearly approximate calendar display only; no precision claim follows from `wall_clock_synced`.

Account separately for: (a) `dropped` known bytes reported by the device since that channel's previous event; (b) increased `rx_overrun_events` where some loss may have unknown size; (c) global `seq` gaps, meaning whole events lost after sequence assignment with unknown byte count; (d) local bounded trace eviction. Empty data with nonzero dropped must produce a loss-only marker immediately. Keep the contract's limitations explicit: a drop marker identifies when loss was reported, not exact missing byte positions, and sequence gaps cannot be translated to bytes. Statistics are cumulative and reconcile known loss only under the contract's stated drained-queue conditions.

The browser and transport must remain bounded under sustained rates up to advertised capability. Establish an explicit maximum in-memory trace and a measured render/update cadence; batch UI updates without altering message order or counters. If the browser cannot keep up, expose growing backlog / delayed rendering and preserve all device-side loss reports. Do not promise lossless capture at 1 Mbaud merely because the UART advertises it. Reliable ordered WebRTC can still buffer, stall or disconnect; define queue/backpressure behavior and maximum message size before enabling Serial over remote mode.

## Session, authentication and security

The Serial contract defines one active logical session per device: a new transport replaces and closes the old connection before hello. Model this independently of the CAN hub's ability to hold several different devices. A second tab or client takeover gets an explicit notice and a user-initiated reconnect; no automatic retry loop.

For direct mode, retain the current exact page-Origin allow-list guidance and HTTPS/`wss://` preference. Origin checks mitigate cross-origin browser access but are not authentication; the contract explicitly leaves authentication/authorization out of scope. A reachable unauthenticated serial bridge could expose sensitive data and permit arbitrary TX, so product deployment needs an authenticated transport/access-control decision before broad LAN exposure. Do not put passwords or long-lived device credentials in browser storage, URL, logs, or the static page. Avoid showing/logging raw payloads in diagnostics by default; payload may contain credentials or proprietary data.

Remote mode requires the current Plotune sign-in, project authorization and short-lived relay ticket flow. A device must authenticate the remote client authorization granted by the relay, and signaling/relay identities must be bound to the selected device. Confirm with the cloud/device owners that Serial bytes and TX are allowed under the same authorization policy and that reconnect/replacement maps cleanly to the single-session rule. Until confirmed, hide remote Serial as unsupported; do not assume CAN authorization automatically covers Serial. Use reliable ordered data semantics; never switch to unordered/unreliable channels for a byte stream without a contract-level recovery design.

## Honest platform and hardware limits

The existing Web README targets Chromium direct WebSocket. Firefox/Safari/iOS restrictions on HTTPS-to-`ws://` and local-network access remain; do not claim cross-browser support from Chromium user-agent simulation. Trusted device `wss://` certificates and native local-network prompts need real-browser validation. The current remote WebRTC adapter is already implemented for CAN messages, but Serial-specific throughput, high-rate backpressure, sustained mobile behavior, relay policy, packetization effects and recovery have not been demonstrated. Reliable delivery at the data channel does not prove the overall device queue is lossless.

Mock Playwright can verify protocol/UI behavior, 64-bit parsing, deterministic loss cases, sequencing, replace-on-connect, origin policy and bounded UI behavior. It cannot establish electrical RS-232/422/485 behavior, isolation, RJ45/Digi pinout, polarity, termination/bias effectiveness, baud accuracy to 1 Mbaud, parity/framing/break detection, two-channel simultaneous operation, actual UART overruns, TX timing, cable length/noise immunity, or hardware queue capacity. Those require the specified Serial board, loopback/peer fixtures and instrumented acceptance procedures. No hardware evidence is implied by this plan.

## Exact Playwright scenarios for Phase 2

Use the production preview and a deterministic contract-faithful mock WebSocket server, following `e2e/mockServer.ts` and `tests/helpers/mockDevice.ts`. The Serial mock should expose request logs, controllable device clock, event injection, queue capacity and link close/replace controls. Every test sets local sign-in off as current preview tests do. These are browser/client contract tests, not hardware tests.

1. **Capability-driven descriptor:** connect a two-channel mock with the required modes and rates. Assert advertised options appear; RS-232 hides/disables termination and bias, RS-485 exposes bias, and missing config is labeled unconfigured.
2. **Second capability profile:** reject a one-channel or missing-required-mode descriptor as incompatible with v0.1.0, without sending control commands.
3. **Version compatibility:** patch mismatch with same 0.x major/minor completes hello; different minor and different major each show unsupported-version notice, issue no status/config calls and close cleanly.
4. **Strict descriptor/event validation:** parameterize malformed uint64, unsupported mode/rate, malformed hex, invalid channel/direction and unknown event shape. Assert protocol notice, connection termination and no fabricated trace row.
5. **Independent atomic configuration:** configure channel 1 to RS-485 and channel 2 to RS-232 with distinct formats. Assert complete configs are sent independently; reject a channel-busy response without changing the displayed effective config; assert no implicit stop/reconfigure/restart occurred.
6. **Start and stop selected channels:** leave one channel unconfigured, select only the configured channel, start and assert only its `start_rx` target; stop and assert queued bytes are rendered before stop completes and status becomes stopped.
7. **Arbitrary bytes and timestamp precision:** inject NUL, `ff`, invalid UTF-8, and bytes around `2^60` timestamps. Assert exact lowercase hex, reversible escaped display, preserved BigInt-derived time and per-channel event order.
8. **Chunk boundaries carry no meaning:** inject adjacent chunks containing halves of a text line and assert the UI does not invent line/message boundaries; concatenated byte export equals the exact input.
9. **Known loss including loss-only event:** inject data with `dropped > 0`, then empty data with dropped bytes. Assert separate markers/counts, exact received bytes, no fabricated placeholders, and appropriate statistics.
10. **Unknown overrun and event sequence gap:** increase overrun event count without known bytes, then skip a global sequence number. Assert two distinct warnings, unknown byte amount remains unknown, and neither is added to known dropped-byte total.
11. **Bounded trace eviction:** reduce trace capacity, inject enough chunks, assert oldest rows are evicted, an eviction count is visible, trace memory/rendered row count remains bounded, and device drop counters remain unchanged.
12. **TX accepted vs sent:** transmit arbitrary bytes including NUL; assert the UI says accepted/queued after response, not physically sent. Later update stats with completed and failed bytes and assert those states/counters are distinct.
13. **Single-session replacement:** connect page A, then connect page B to same mock; assert A shows replacement notice and stops stream updates, B performs a fresh hello and displays actual stream/config state. Assert neither page auto-reconnects.
14. **Disconnect and bounded queue on reconnect:** while RX remains armed, close transport, enqueue within mock capacity and overflow beyond it, reconnect manually. Assert new session ID, original device timestamps, actual streaming state, and explicit dropped count/loss marker.
15. **Origin and insecure-origin guidance:** mock refuses an unlisted hosted origin and accepts the configured exact origin; assert generic connection failure guidance does not claim authentication. Verify secure page plus `ws://` follows browser policy notice/attempt handling already used by Web.
16. **Remote policy gate:** until cloud authorization is explicitly enabled for Serial, assert remote Serial is not offered. When enabled in a later phase, use a fake relay/WebRTC adapter to verify ordered delivery, close/replacement, max payload/backpressure notice and no credential/payload leakage to logs.
17. **Accessible responsive live view:** at desktop and 390px widths, keyboard-operate configure/start/stop/TX, scan with axe, and assert live updates use an announced summary rather than announcing every byte chunk.

## Review risks and decisions to close

- **Contract persistence ambiguity:** saved configuration is required conceptually but storage and save timing are unspecified. Firmware and UI tests need a stable rule for power-cycle expectations.
- **Version field ownership:** clarify whether `hello` includes the client version and whether the response has an explicit capability profile discriminator. Web must distinguish CAN and Serial before choosing a decoder.
- **Queue and payload sizing:** 4096-byte request cap conflicts with arbitrary-length TX in principle; contract must set an explicit maximum transmit bytes and transport payload/message bounds. Define sustained event chunk sizing too.
- **WebRTC remote authorization:** existing remote CAN path is not evidence of Serial entitlement, rate, or queue safety. Keep remote disabled until cloud/device policy and measured load behavior are accepted.
- **Rate claims:** UI capability lists may include 1 Mbaud, but mock tests and the browser alone cannot demonstrate lossless capture at that rate. Product copy must state configured capability and report measured loss.
- **Error marker semantics:** overrun bytes are subsets of dropped bytes and may be unknown; the UI can easily double count if statistics and event markers are combined. Keep event and cumulative counter views separate or reconcile by clear counter windows.
- **Trace display semantics:** byte chunk boundaries are not application records. Avoid newline assumptions, Unicode replacement loss, or visual claims that mark an exact loss location.
- **Authentication:** Origin allow-lists are not authentication. LAN direct mode needs an access-control story appropriate for sensitive serial traffic and arbitrary TX.
- **Hardware-specific proof:** electrical standards, connector pinout, isolation, termination/bias and actual error detection need explicit hardware gates; simulator acceptance cannot close them.
- **Browser matrix:** existing local-network prompt is native and simulated in Playwright. Safari itself, iOS, real Firefox, trusted device certificates, and high-rate mobile rendering remain separate qualification work.
